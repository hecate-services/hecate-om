## The one line this exists for

So `hecate_om` itself is built directly on macula's **supervised** primitives (`macula_client`, `macula_publisher`, `macula_subscriber`, `macula_response`/`macula_streamer` advertise, `macula_feeder`/`macula_download`) — not on raw `macula:publish/4`-style calls — and so every `hecate-services/hecate-X` provider gets that supervision for free, the same way it already gets connection lifecycle and RPC-consumer calls for free.

**The point of the 2026-08-24 session-2 survey was explicitly two-sided, not just cataloguing duplication:** (1) does the supervised API, read directly rather than assumed, already cover what ~20 hand-rolled implementations built for themselves — and where it does, hand-rolled code isn't evidence for the wrapper's *design*, it's a list of things the wrapper makes obsolete; (2) where the hand-rolled code reveals a real requirement the supervised primitive's own surface doesn't dictate (a realm parameter, an outcome-handling mode, a dynamic set of topics), that's a genuine design input for `hecate_om`'s wrapper API, not for macula itself. Getting this backwards — designing the wrapper to match what the hand-rolled code does, instead of what the supervised primitive already provides — was a real mistake made once in this plan's first draft of pieces C and D (see the "CORRECTED" notes below) and is exactly the failure mode this section exists to warn against.

## Why now, with evidence

- The original survey (2026-08-21/22) found four DIY modules hand-rolling raw `macula:subscribe`/`publish` because `hecate_om` gave them nothing, and one confirmed gap: `hecate_om_capabilities` only writes DHT discovery records, it never calls `advertise_direct`, so a service is discoverable but not callable.
- `hecate-services/hecate-tube` was deliberately built as one complete exemplar exercising all four primitive pairs (RPC, PubSub, Content, Streaming) against raw SDK primitives on purpose, specifically so this design would come from one real, finished service instead of fragments. It's now built and live (2026-08-23). Full audit in the handover doc.
- A workspace-wide grep across all 23 `hecate_om`-consuming repos (this session, 2026-08-24) found the pattern is far more widespread than the original four-module survey knew: **9 repos** with their own hand-rolled `advertise_direct`/`macula:advertise` provider wiring, **14** with their own `macula_subscriber`/`macula:subscribe`, **17+ repos** (24+ modules) with their own `macula_publisher`/`macula:publish`, and (so far) only `hecate-tube` with hand-rolled Content wrapping. Full list in the handover.
- Two independent implementations of "supervised advertise, with periodic re-assert" already exist (`hecate-tom-world`'s `tom_advertiser.erl` / `hecate-tom-ocean`'s `tom_ocean_mesh.erl`, and `hecate-tube`'s `tube_mesh_providers.erl`) and at least the latter encodes a genuinely hard-won, non-obvious lesson (below) that would otherwise get rediscovered the hard way by the next service that needs it.

## Scope: six pieces

Each piece: what it is, why, what to derive it from (concrete source, not guessed), the open question(s) that need settling before code, and how to know it's actually done (not just compiling).

### A. Connection lifecycle: `hecate_om_identity` onto `macula_client:child_spec/3` — IMPLEMENTED 2026-08-25

**What:** Replace `hecate_om_identity`'s hand-rolled `self() ! connect` / 5s-retry / manual `erlang:monitor` + `DOWN` reconnect with `macula_client:child_spec/3`, embedded as a proper supervised child. Keep cert loading, keypair self-heal/persist/puzzle-harden, org/realm/CA resolution exactly as they are — those are Hecate identity concerns, not the SDK's job, and stay layered as a thin wrapper around the pool.

**Why:** Verified this session by reading `macula_client.erl` directly (not assumed): `connect/2` (the `child_spec/3` start MFA) returns immediately even with zero seeds connected; each seed link dials independently, retries forever on its own timer (`?LINK_RESPAWN_DELAY_MS`) without touching the supervisor, and never crashes the pool process for an unreachable seed. That's exactly the resilience `hecate_om_identity` hand-built, already free in the SDK. We cannot justify keeping two implementations of the same thing once one is confirmed to already do the job.

**Open question, resolved by attempting the migration, not by more reading:** `hecate_om_identity`'s own comment claimed a real, previously-observed bug — "hecate_om may start before the macula SDK app is fully up, so a single inline connect races it and loses." `hecate_om.app.src` already lists `macula` in `applications`, so standard OTP boot ordering should prevent this in a real release boot. **Confirmed clean, not reproduced**: `test/hecate_om_mesh_pool_SUITE.erl`'s `seeds_configured_starts_pool_without_a_retry_loop` boots `hecate_om` as a real OTP application (`application:ensure_all_started/1`, not `hecate_om_identity` standalone) and asserts `hecate_om:macula_client()` resolves to a live pid with **no poll or retry on the assertion itself** — under the old hand-rolled design this would have been flaky (the client only attached after `handle_info(connect)` got scheduled); under supervised-child startup the pool is a live pid by the time `ensure_all_started/1` returns, full stop. The live-station equivalent (`test_live/hecate_om_mesh_pool_live_station_tests.erl`) proves the same thing against a real station, not just an unreachable one. The race was real code (the hand-rolled retry existed for a reason once), but not a real boot-ordering hazard once `hecate_om.app.src`'s own `applications` dependency is honored by normal OTP startup — the fix removed dead-weight defensive code, it didn't paper over a live bug.

**Design decision found while implementing, not in the original plan:** the pool is **not** folded into `hecate_om_identity`'s own gen_server state — it's a genuinely separate sibling child in `hecate_om_sup`'s children list (`hecate_om_identity:start_mesh_pool/0` as its start function, registered locally as `hecate_om_mesh_pool` so `macula_client/0` can find it with a plain `whereis/1`, no gen_server round trip). Folding it into identity's state would have kept the same problem piece A exists to remove: something in this codebase deciding when to notice and react to a pool crash, instead of OTP's own `restart => permanent` doing it for free. The pool child is **conditionally included** — omitted entirely when no seeds are configured, exactly matching pre-migration behavior (`macula_client/0` → `{error, no_client}` forever), rather than always starting a real-but-permanently-idle pool that would make "nothing configured" indistinguishable from "connected" to any caller checking `mesh_handles/0` in isolation. This was a real design fork: pieces B–F's own testing strategy treats a real zero-seed pool as the correct representation of "degraded, no mesh" (`macula_client:connect([], #{})`, technique 2) — but piece A chose parity with the existing external contract over that internal convention, since A's own sequencing note says it "touches the one thing every deployed consumer already relies on" and B–F chose the opposite tradeoff (purely additive, free to pick the technically cleaner shape) for the opposite reason.

**Acceptance, met:** every existing `hecate_om_identity_tests.erl` case still passes (unchanged — `keypair_from/1` wasn't touched), plus 4 new pure tests for `configured_seeds/0` (now exported for `hecate_om_sup`'s own use, previously private and untested). `test/hecate_om_mesh_pool_SUITE.erl` (3 new CT cases): zero seeds → no pool child, `{error, no_client}`; seeds present → pool child starts, live pid, no retry loop needed (the boot-race question, above); pool pid killed → OTP's own supervisor brings up a new one (the actual point of "embedded as a proper supervised child" — proving `hecate_om_identity` no longer has any reconnect code to test, because there isn't any). `test_live/hecate_om_mesh_pool_live_station_tests.erl` proves the resulting pool is genuinely usable end-to-end against a real station, not just alive: `mesh_handles/0` resolves and a real piece C publish succeeds through it. "A station restart mid-run reconnects without service restart" is not independently re-tested here — it's inherited for free from `macula_client`'s own per-seed-link retry-forever behavior (already established) and macula's own `macula_link_respawn_replay_tests.erl` (this session, SDK layer); piece A's own tests instead prove the thing actually new here, that a *pool-process* crash recovers via OTP rather than hand-rolled code. 57 EUnit (was 53) + 14 CT (was 11), all green; `rebar3 lint` clean.

**Sequencing note:** done **separately** from B–F, as planned — landed after all of B–F, with their full test suite as the regression net, touching the one thing every deployed `hecate-services/*` consumer already relies on.

### B. RPC provider-side wiring in `hecate_om_capabilities` — IMPLEMENTED 2026-08-24 (uncommitted)

`src/hecate_om_capabilities.erl` rewritten (moduledoc, state, advertise-side internals), `src/hecate_om_service.erl`'s `capability()` type extended, `test/hecate_om_capabilities_tests.erl` extended — 17/17 tests passing (4 new), full suite 30 EUnit + 11 CT green, `rebar3 lint` clean.

**Design correction found while implementing, not caught by the survey:** the "does the RPC path need `advertise_direct` at all" question wasn't actually open — `hecate_om_capabilities`'s own `call_capability/5,7` (already shipped, unchanged by this piece) resolves providers from the DHT and dials them via `macula:call_station/6,7,8` — direct-dial, by design, not pool-routed `macula:call/4`. Per `RPC_GUIDE.md`, `call_station`-reachable handlers *require* `advertise_direct` registration ("a plain advertise publishes no discoverable record"). So the `dns`/`git`/`llm`/`rag` finding (plain `advertise/5`, no reconnect defense needed) was correct for *their* ad hoc, undiscoverable RPC modules, but doesn't apply to `hecate_om_capabilities` itself, which is architecturally committed to direct-dial. Read `src/macula_response.erl` directly to settle it: `advertise_direct/6,7` already does exactly what `hecate_om_capabilities` was hand-rolling *half* of — `advertise/6` (registers the handler, pool-stored) **then** `macula_direct_dial:publish_advertisement/5` (writes the same `procedure_advertisement` record `build_advertisement/5,6` was hand-building), plus the `reuse_sup` option (added to macula for exactly this re-advertise-without-leaking need) and a `cert_chain` option matching the existing Slice 7c dual-trust support. **So piece B isn't "add a handler call alongside the existing DHT write" — it's "replace the hand-rolled half with the one call that already does both halves correctly."** Keeping both would have recreated the exact two-sources-of-truth pattern the survey caught causing `hecate-rag`'s real dispatch-shape bug.

**What was built:** a capability carrying `handler => {Module, Args}` (`Module` implementing `-behaviour(macula_response)`) is advertised via `advertise_direct/7`, with each capability's factory-supervisor pid round-tripped through a new `advertise_sups` state field and passed back in as `reuse_sup` on every 30s republish tick — no supervisor leak. A capability with no `handler` key keeps the legacy record-only path unchanged, for backward compatibility. `has_handler/1` and `reuse_sup_opts/1` exported as pure, directly-testable dispatch helpers (same convention as this module's existing `procedure_uri/3`/`build_advertisement/5,6`, and as piece C's `resolve_realm/2`).

**The MFA-pair-not-closure requirement turned out to already be structurally satisfied, not something to add:** `macula_response:advertise/6` takes a `Module` atom + `Args`, dispatched fresh via `Module:init/1`/`Module:handle_request/2` *at each inbound call*, not a fun captured at advertise time — there is no closure to pin a stale code version in the first place. `tom_advertiser.erl`'s hand-rolled-fun problem doesn't exist when built on `macula_response`.

**Realm override:** already free — `advertise_direct/6,7` takes `Realm` as a plain argument, same as `macula_publisher` in piece C. No design work needed here either.

**Not yet done, deliberately out of scope for this pass, same reasoning as piece C:** porting `hecate-dns`/`-git`/`-llm`/`-rag`'s `*_mesh_rpc.erl` modules or `hecate-embedder`'s advertiser onto this. Also not done: `macula_streamer:advertise_direct/6,7` (the streaming half of the original piece B scope) — kept out of this pass; streaming has a different callback shape and no capability-declaration precedent yet in `hecate_om_service`, and folding it in would have doubled this piece's surface without new evidence to design it from (hecate-tube's `stream_video_clip_by_id.erl` is the only streaming-provider example in the whole survey). Worth its own follow-on once a second streaming exemplar exists.

**UPDATED, same session — the strong acceptance criterion is now fully met, against a real station, and it found two real pre-existing bugs.** Asked directly whether the demo fleet could just be used (it's documented, disposable dev infra — nothing was stopping this), so `test/hecate_om_capabilities_live_station_tests.erl` was written against `station-de-frankfurt.macula.io` (re-`dig`ged live, confirmed current — see `reference_demo_fleet_boxes` memory). First attempt failed, and root-causing it live surfaced two real, pre-existing bugs in `hecate_om_capabilities`'s already-shipped consumer side (`call_capability`), neither introduced by piece B's write-side work — piece B's live test was simply the first thing to ever exercise that code end-to-end:

1. **`resolve_at/4`/`resolve_full/4` keyed DHT lookups by `procedure_uri/3`** (Realm+Org+Name), **but a handler-bearing capability is written under macula's own `discovery_uri/2` key** (Realm+bare-Name — `macula_direct_dial.erl`'s own comment: "No Org segment... Org is only consulted post-resolve"). `call_capability`'s own dial side already used the bare name (`macula:call_station(..., CapName, ...)`), so the read side's Org-inclusive key was never going to match what a handler-bearing capability is actually reachable under. Fixed with a new `discovery_key/2` (exported, pure) replicating macula's private formula; `procedure_uri/3` and the legacy record-only path are untouched, so existing tests are unaffected.
2. **`dial_provider` called `macula:call_station/7` with no trust override**, so every direct-dial call failed at the TLS layer (`{error, not_connected}`, misleadingly generic) before the application-level trust check — the DHT record's pubkey signature — ever ran. `macula_direct_dial:call/6` (macula's own canonical resolve-then-call implementation) sets exactly `#{verify => none, pin_tls_cert => false, expected_node_id => Station}` for this reason, with a comment explaining why: "trust is pinned to the exact pubkey the signed DHT chain resolved, but enforced at the application layer, not the TLS layer — a production station's TLS certificate has no relationship to its macula identity." `hecate_om_capabilities` was missing this triad entirely. Fixed by matching macula's own convention exactly, `Station` now threaded through to `dial_provider`.

Both were diagnosed with real, live evidence (not guessed): `lookup/1` succeeding while `call_capability` failed with the same key isolated bug #1; direct debug instrumentation of `resolve_endpoint`/`macula:call_station`'s actual return values, plus ruling out same-identity-two-connections and DHT-propagation-timing as competing hypotheses (a separate consumer identity/pool made no difference; the record was stable across repeated `lookup/1` calls), isolated bug #2. Final test: two independent pools/identities (provider + consumer, matching a real deployment), full round trip, `{ok, #{echo := #{ping := <<"pong">>}}}` — note the reply keys arrive as atoms, confirming the session's separate atom-key wire finding live, for the first time end-to-end, as a bonus.

**Acceptance, now fully met:** a handler-bearing capability's `register/1`/`publish/0` reach `advertise_direct` and degrade cleanly without a station (unit-tested). `reuse_sup` is the exact pid from a prior call (pure-tested). **Genuinely callable mesh-to-mesh, from an independent consumer identity, against a real station — proven live.** 31 EUnit (was 30) + 11 CT, all green; `rebar3 lint` clean. The live test runs as part of the default `rebar3 eunit` (fast, ~1s) — not excluded, a deliberate tradeoff given this repo already treats the demo fleet as safe dev infra; move it to a separate profile if it ever proves flaky in CI, don't delete the coverage.

### C. `hecate_om_pubsub:publish/2,3` — IMPLEMENTED 2026-08-24 (uncommitted)

`src/hecate_om_pubsub.erl` + `test/hecate_om_pubsub_tests.erl` written and passing (9/9 new tests; full suite 26 EUnit + 11 CT, all green; `rebar3 lint` clean). Matches the corrected design below: `publish/2,3` and `publish_many/2,3`, built on `macula_publisher:start_link/6`, all three outcome modes, realm override. `resolve_realm/2`/`resolve_mode/1` exported as pure helpers (same convention as `hecate_om_capabilities.erl`) — needed because `macula_publisher` ships to hex without `debug_info`, so `meck`'s `passthrough` mode can't wrap it here; testing the resolution decision directly sidesteps that and is arguably the better test anyway. Live-outcome tests use a real zero-seed `macula_client:connect([], #{})` pool (no station needed) so `sync`/`async_log` are proven against a genuine SDK `{error, {transient, no_healthy_station}}`, not a stub — `async_log`'s warning was confirmed to actually fire in the test run.

**Not yet done, deliberately out of scope for this pass:** porting any of the ~20 hand-rolled call sites in the migration table below to actually call this. That's a separate, per-repo follow-on once C itself is reviewed — implementing the wrapper and proving its own behavior is a different unit of work from migrating consumers onto it. Also new to this repo: a `{profiles, [{test, [{deps, [meck]}]}]}` block in `rebar.config` (`~> 0.9`, matching macula's own pin) — worth knowing if another piece's tests want the same tool.

**Design (as implemented):**

**RE-CORRECTED, 2026-08-24 session 2 (second pass) — went one step too far the first time.** The first pass of this session concluded piece C should wrap raw synchronous `macula:publish/4` because ~20 hand-rolled repos do exactly that. That's backwards: those ~20 repos hand-roll raw calls *because `hecate_om` gives them nothing better*, not because `macula_publisher` (the SDK's own supervised behaviour, read directly from `src/macula_publisher.erl` this session) is unfit for the job. Reading it settles what actually needs designing:

```erlang
-callback init(Args) -> {ok, State} | {stop, Reason}.
-callback handle_published(Result :: ok | {error, term()}, State) ->
    {noreply, NewState} | {stop, Reason, NewState}.

macula_publisher:start_link(Module, Pool, Realm, Topic, Payload, Args)
```

It already takes `Pool`/`Realm`/`Topic` as explicit arguments (realm-override is not a gap to design, it's already there), delivers the outcome to a callback the *caller* fully controls (silent / log / return-to-caller are three different one-line `handle_published/2` bodies, not three designs to reconcile), supports cancellation, and — a real capability none of the ~20 hand-rolled call sites have today — auto-publishes `pubsub.publish_started_v1`/`pubsub.publish_completed_v1` lifecycle facts (with `outcome => completed | failed | cancelled`) around every publish, for free. **What:** `hecate_om_pubsub:publish/2,3,4` starts a `macula_publisher` with a default callback module `hecate_om`'s own `handler => sync | async_log | async_silent` option selects (or a caller-supplied module for anything else), reading `mesh_handles/0` internally for Pool and defaulting Realm to `hecate_om_identity:realm()`.

**What the survey actually contributes here — real requirements for the *wrapper's calling convention*, not for the SDK primitive:**
1. **Optional realm override**, defaulting to `hecate_om_identity:realm()` — confirmed a real deployed need by `hecate-robo-rumbler`, `hecate-biotope`/`hecate-society`, and `hecate-dronex` (piece B), all publishing to a second, non-fleet realm off the same pool. `macula_publisher:start_link/6` already accepts `Realm` as a plain argument, so this is purely "don't hardcode it in the wrapper," not new SDK work.
2. **A caller-selectable outcome-handling mode** (`sync` — block and return `ok | {error, _}`; `async_log`; `async_silent`, the current default nobody asked for but most callers use) implemented as three tiny stock `handle_published/2` bodies. `hecate-grid`/spartan mostly want `async_silent`; `hecate-victron`/`hecate-warden`/`hecate-sentinel` want `async_log`; `hecate-biotope`/`hecate-society`/`hecate-mpong-bot` want `sync` (they return `{error,_}` to their own caller today, meaning they're already blocking — `sync` mode just moves that blocking into the wrapper).
3. **N-topic fan-out convenience.** `hecate-news` publishes one fact to up to 4 topics per call. Add `publish_many/2,3` (loop `publish/2,3` per topic) rather than complicating the base signature — `macula_publisher` itself is single-topic by design and shouldn't be bent to fit this.

**Closest existing prior art, worth reading directly as a skeleton for the wrapper's *outer* API (not for how it talks to the mesh — that part should go through `macula_publisher`, which none of these do):** `hecate-mpong-bot/src/hecate_mesh.erl` — already a small, generic publish/subscribe/unsubscribe facade over pool+realm with degrade-to-`{error, mesh_unavailable}` semantics.

**Migration payoff:** once this ships, every one of the ~20+ hand-rolled `catch macula:publish(...)` call sites found this session (spartan's ~10, parksim's 6, grid/news/victron/warden/biotope/society/mpong-bot/archive/sentinel/robo-rumbler/dronex/tom-ocean/tom-world) becomes a direct one-line replacement — see the migration table in the root doc.

**Acceptance:** existing publish call sites in at least one already-hand-rolled repo (spartan or parksim give the most call sites to prove the abstraction against) can be ported to `hecate_om_pubsub:publish/2,3` with a net line reduction and no behavior change, verified by that repo's own tests still passing. Additionally verify the realm-override and each outcome-handling mode against a repo that actually needs it (dronex/biotope for realm; biotope/victron for `sync`/`async_log`) — don't just prove it against the `async_silent` default, since that's the minority-need case among real callers, not the representative one. Also verify the free lifecycle facts (`pubsub.publish_started_v1`/`_completed_v1`) actually land on the mesh — that's a new, testable capability this migration adds, not just a refactor.

### D. Declarative `subscriptions/0` + `hecate_om_pubsub:ensure_subscriptions/1` — IMPLEMENTED 2026-08-24 (uncommitted)

Three new modules: `hecate_om_pubsub_sup.erl` (plain `one_for_one` supervisor, empty at boot, children added/removed dynamically, `restart => transient`), `hecate_om_pubsub_subscriptions.erl` (gen_server holding the desired set + a 30s reconcile tick, same shape as `hecate_om_capabilities`'s own republish timer, for the same reason — self-heal a topic that couldn't start yet, or whose child exhausted its restart budget after a full pool replacement), and `hecate_om_pubsub:ensure_subscriptions/1` (thin delegator). `hecate_om_service:subscriptions/0` is a new optional callback, wired by `hecate_om:boot/1` exactly like `store_id/0`/`read_model_id/0`. Both new processes added to `hecate_om_sup`'s tree.

`diff/2` (desired vs. currently-running topics → `{ToStart, ToStop}`) is exported as a pure, directly-testable function — same convention as pieces B and C.

**Verified with real event delivery, not just wiring**, against the same live station used for piece B (`station-de-frankfurt.macula.io`): declared a subscription, published a real fact via piece C's `hecate_om_pubsub:publish/2`, and confirmed the declared handler module actually received it via `macula_subscriber:handle_event/4` — proving the full boot→subscribe→receive path, not a callback-registration assertion. Then proved the dynamic-set design directly: adding a second topic left the first child's pid unchanged and started exactly the new one; removing the first topic stopped exactly it and left the second untouched. Confirms the "supervision-membership, not reconnect-detection" design conclusion from the earlier `macula_subscriber`/`macula_client_replay` source read holds up under real use, not just in theory.

**Found and fixed a real bug in this codebase's own test-teardown convention along the way (not a piece-D design bug):** `supervisor:stop/1` does not exist in OTP — verified directly (`erlang:function_exported(supervisor, stop, 1)` → `false` on OTP 28 here) — I had assumed it did, by analogy with `gen_server:stop/1`. Using it silently `undef`'d inside a `catch`, leaving the supervisor alive across test modules and causing an `already_started` collision the next time a test tried to start the same globally-registered name. Fixed with the correct idiom: `unlink/1` (so the shutdown exit signal doesn't propagate back and kill a non-trapping caller) + `exit(Pid, shutdown)` + a monitor-wait for confirmation. Worth checking whether any *other* test file in this repo or elsewhere in the workspace uses `supervisor:stop/1` under a `catch` and is silently leaking supervisors the same way — not audited here, flagging it.

**Acceptance, fully met:** a service declaring `subscriptions/0` receives events without touching raw `{macula_event, ...}` (proven live). `ensure_subscriptions/1` against a dynamic set starts exactly the new child and touches nothing already running, and stops exactly a removed one (proven live, both directions). Degrades cleanly with no mesh (unit-tested, matching every other piece's contract). 1. **Ordinary link churn is already invisible to a subscriber.** `macula_client_replay:subs_to/2` mirrors `advs_to/2` exactly: on every link respawn, the pool re-issues a SUBSCRIBE frame for every `{Realm, Topic}` it's tracking, using the *same* `SubRef`. 2. **`macula_subscriber` turns a *genuine* subscription loss into a process stop**, not a message to react to: `handle_info({macula_event_gone, SubRef, Reason}, State) -> {stop, Reason, State}`. ### E. `hecate_om_content:put/1,2` / `get/1,2` — IMPLEMENTED 2026-08-24 (uncommitted)

`src/hecate_om_content.erl` + `test/hecate_om_content_tests.erl` + `test/hecate_om_content_live_station_tests.erl`, matching the design below with no corrections needed this time — reading `macula_feeder.erl`/`macula_download.erl` directly confirmed the plan's assumption exactly (`macula_download`'s own moduledoc: "Only chunked content is discoverable this way", verbatim what hecate-tube's own comment already said).

**What was built:** `put/1,2` and `get/1,2`, always via the pooled `macula_feeder:start_link/5` / `macula_download:start_link/5` — never `start_link_direct`. One shared `init/1` serves both `macula_feeder` and `macula_download`'s callback contracts (`Args = {Pid, Ref}` either way); `handle_fed/2` and `handle_downloaded/2` have different names so there's no collision there — but declaring `-behaviour(macula_feeder)` *and* `-behaviour(macula_download)` together does collide (both declare `init/1`) and the compiler rejects it outright, "conflicting behaviours", even though one shared implementation genuinely satisfies both contracts. Separately, `put/2`/`get/1` shadow the auto-imported `erlang:put/2`/`erlang:get/1` process-dictionary BIFs — the same well-known clash `dict`/`maps`/`ets` all resolve with `-compile({no_auto_import, [put/2, get/1]})`.

**Acceptance, fully met:** round-trips a small (non-chunked) blob through the pooled path (done, live, real station). **Naming/design discussion, same session, worth recording — the split modules were renamed and the underlying design choice was interrogated, not just the names.** Initially named `hecate_om_content_put.erl`/`hecate_om_content_get.erl` (operation-first, matching the facade). Challenged directly: since these two files carry zero domain content of their own (every real behavior — mesh handle resolution, realm override, timeout, cancel-on-timeout — lives in the facade), naming them after the *operation* implies meaning they don't have; the single salient fact about each is *which SDK contract it satisfies*, forced into existence only because `macula_feeder`/`macula_download` can't share one `init/1'. Renamed to `hecate_om_content_feeder.erl`/`hecate_om_content_downloader.erl` — contract-first, matching macula's own vocabulary for the thing being wrapped, while the facade (`hecate_om_content.erl`) keeps operation-first naming (`put`/`get`) since that's what a *caller* reaches for. Different salient fact at each level, different vocabulary — both still "screaming," just about different things.

The broader question raised alongside it — given pieces B and D deliberately leave the callback to the *service's own* handler module (`capabilities()`'s `handler`, `subscriptions()`'s `HandlerMod`), why does piece C (publish) and this piece (content) instead have `hecate_om` own the callback and hand back a terminal, synchronous value? Re-examined, not just defended: B and D's callbacks (`handle_request/2`, `handle_event/4`) *necessarily* carry business logic — hecate_om cannot know what an RPC call means or what a subscribed event should trigger. C and E's callbacks (`handle_published/2`, `handle_fed/2`, `handle_downloaded/2`) do not, in any real example surveyed — every one of ~20 hand-rolled publish call sites and hecate-tube's own content wrappers used the callback purely as a value-relay ("tell me if it worked"), never for embedded per-service logic. The split tracks that distinction, not an inconsistency — same evidence-driven method the rest of this plan uses.

**Pushed further, same session — asked to imagine the service that *does* need it, and build for it.** Concrete case: a batch publisher (fire 500 facts without blocking, retry-with-backoff on individual failure, fully decoupled from any caller) or a batch content upload (per-item completion side effect — a progress counter — without blocking on each one). None of piece C's three modes or piece E's block-and-return shape cover this, and nothing *stops* a developer from hand-rolling their own `-behaviour(macula_publisher)`/`macula_feeder`/`macula_download` module to get it today — but doing so means losing the one thing these wrappers actually earn their keep on (`hecate_om:mesh_handles/0` resolution), forcing exactly the boilerplate duplication this whole plan exists to eliminate. So the fix isn't "C and E were designed wrong" — it's "the terminal API should coexist with a thin escape hatch," matching how `macula` itself offers both a facade call and the underlying supervised behaviour.

**Added:** `hecate_om_pubsub:start_publisher/3,4,5` and `hecate_om_content:start_feeder/2,3,4` / `start_downloader/2,3,4` — each resolves `hecate_om:mesh_handles/0` exactly like the terminal functions, then starts the real SDK behaviour with a **caller-supplied callback module**, handing back `{ok, Pid} | {error, mesh_unavailable | term()}` (not a blocked-until-done value). `hecate_om` has no say over what the caller's own callback does with the outcome — full parity with what piece D already gives `subscriptions()`. This makes the earlier design split fully honest rather than merely defensible: the generic terminal path stays the default (still what every real example surveyed needed), and the harness path piece B/D already had is now available for C/E too, for the day a real service needs it — additive, doesn't touch any existing caller. Renamed the private mode-dispatch helper in `hecate_om_pubsub.erl` (`start_publisher/6` → `publish_with_mode/6`) to avoid a same-name-different-arity clash with the new public function.

Tested the same way as the terminal APIs: degrade-without-mesh (unit), and — for the escape hatch specifically, since its entire point is delegation — a live round trip through a **test-owned callback module**, not `hecate_om`'s own, against the real demo-fleet station, proving the caller's module genuinely receives the SDK outcome. 46 EUnit + 11 CT, all green; `rebar3 lint` clean.

**Pushed a third time, same session — asked whether delegation alone actually proves the motivating scenario, not just that a message arrives.** It didn't. Built the *actual* retry-with-backoff coordinator described above, run to genuine exhaustion against the zero-link pool (3 real attempts, in order, with real 50ms backoff between them), and a batch-upload coordinator for content, run to real completion against the live station (3 concurrent uploads, a shared collector, distinct MCIDs). Both are now real EUnit tests, not just design-doc claims.

**The first version of the pubsub retry test was genuinely flaky, not just tight on timeout margin — and the fix is a real design lesson, not a bigger number.** It called `start_publisher/4` again *recursively from within* `handle_published/2`, i.e., from inside a `macula_publisher` gen_server's own callback, in the same beat that gen_server was about to `{stop, normal, ...}`. That passed in isolation and under light load, then failed deterministically once run inside the full suite (more concurrent process churn), and inserting diagnostic `io:format` calls — which perturbs scheduling — made it pass again, the classic signature of a real race, not bad luck. Raising the timeout made it *worse*, not better: it stopped failing fast and instead hung for the outer EUnit group's 15s budget before being cancelled. The actual fix was moving the retry decision into a **separate, ordinary process** that orchestrates N one-shot `start_publisher/4` calls (each using the already-proven `{simple, Pid}` relay), rather than looping inside a short-lived per-attempt callback. Confirmed clean over 8 isolated runs and 3 full-suite runs. This is also simply the *more correct* design for "fully decoupled from any caller waiting synchronously," which was the original justification for building the escape hatch at all — not a workaround bolted on after the fact. Worth remembering if a real service ever builds retry logic on `start_publisher`/`start_feeder`/`start_downloader`: put the loop in your own process, not in the SDK behaviour's own callback.

47 EUnit (was 42) + 11 CT, all green across repeated runs; `rebar3 lint` clean.

## Testing strategy — as it actually turned out, plus CI (2026-08-24)

The pre-implementation version of this section proposed reusing `hecate-testkit`'s `with_mesh/1,2` in-memory cluster. That never happened — what actually emerged across pieces B–E, derived from what each piece genuinely needed rather than planned in advance, was three techniques, escalating in realism:

1. **Pure functions** (`resolve_realm/2`, `resolve_mode/1`, `has_handler/1`, `reuse_sup_opts/1`, `diff/2`) — the decision logic exported and tested directly, no mesh at all. Same convention `hecate_om_capabilities.erl` already used for its record-building helpers before this plan existed.
2. **Zero-seed real pool** (`macula_client:connect([], #{})`) — a genuinely real `macula_client`/`macula_publisher`/`macula_subscriber` boots and runs, but with no station to reach, so outcomes resolve to real, deterministic SDK errors (`{error, {transient, no_healthy_station}}`) fast and locally. Covers every degrade/failure-mode assertion for pieces B–D without touching a network. This is what most of `test/*.erl` is.
3. **Real demo-fleet station** (`station-de-frankfurt.macula.io`) — the only way to prove a *success* path (a capability genuinely answers a call, a subscription genuinely receives a published event, content genuinely round-trips) and, as it turned out, the only way three real bugs (piece B's DHT key mismatch and missing TLS trust triad, the `supervisor:stop/1` teardown bug, and — caught by a fork of this same rigor — the recursive-retry-inside-a-dying-callback race) were ever going to surface. Every acceptance criterion that says "verify X actually happens" turned out to mean this, not a callback-registration assertion.

**CI split, 2026-08-24.** Technique 3's tests live in `test_live/`, not `test/` — `rebar3`'s own default eunit/ct discovery path is `test/`, so a new test file is part of the always-run, CI-gated suite by default unless someone deliberately places it in `test_live/`; the safety comes from directory placement, not a maintained exclusion list that can silently go stale as files are added. `rebar.config`'s `live_test` profile (`{extra_src_dirs, ["test_live"]}`) makes them reachable via `rebar3 as live_test eunit --dir test_live`. CI (`.github/workflows/lint-and-test.yml`) now runs `rebar3 lint` + `rebar3 eunit` (fast, local, techniques 1–2 only, ~0.6s) + `rebar3 ct` as the blocking gate, plus a separate `live-mesh-tests` job (`continue-on-error: true`) so a real regression is still visible without letting a demo-fleet blip block an unrelated merge. Before this, CI ran `rebar3 ct` only — none of pieces B–E's test coverage, including everything that ever caught a real bug, was running automatically at all.
